RedisNearCache Mechanics

A near cache whose entries are invalidated by the Redis server itself. This page shows the parts, the message flow, and the failure cases that shaped the design.

The one-sentence version

Your app keeps an in-process copy of the Redis values it reads. Redis remembers which keys each tracked connection has read, and when any client writes one of those keys, Redis pushes a message naming it, and the local copy is thrown away. Nothing in the write path has to cooperate. A Java service, a Go job, or someone at redis-cli all invalidate you the same way.

Why not an app-level backplane

FusionCache and the proposed HybridCache backplane solve staleness with pub/sub that the writer publishes to. That only works when every writer uses the same library. Server-assisted tracking moves the responsibility to the one place every write already passes through.

The parts

The package never touches your existing multiplexer. It opens one private StackExchange.Redis multiplexer, forced to RESP2 and admin mode, which gives it two connections per Redis node: an interactive connection for reads, and a subscriber connection that Redis is told to send invalidations to.

A read, a hit, and an invalidation

The in-flight race

An invalidation can arrive between sending GET and storing its reply. Without a guard the stale reply would be cached with nothing left to evict it, because the server already sent its one invalidation. Each read records a version token when it starts; an invalidation bumps the key's version; the reply is stored only if the version is unchanged.

Reconnects, the part that actually needs care

Tracking is per-connection state on the server. The spike showed two silent failure modes, both handled by re-arming and flushing.

Per-endpoint state

Cluster

Client ids and tracking tables live on each node, and a node sends invalidations only for keys it owns. The private multiplexer already keeps an interactive and a subscriber connection per master, so the armer repeats the same dance per node with that node's subscriber id.
